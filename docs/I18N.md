# Languages

English, Hindi and Marathi ship today. Adding a fourth is one file and one line.

## How it works

The rule the whole thing rests on: **no module ever produces display text.**
The engine returns keys (`driver.waterDeficit`, `factor.irrigationMm`), and
whoever renders them looks the key up in the active language. That is why the
explanation sentences, the risk drivers and the freshness badges all switch
language — not just the labels.

Lookup order for any key:

```
active language  →  English  →  the engine's built-in fallback  →  the key itself
```

So `en.json` does not repeat the engine's strings, and a Marathi key you have
not translated yet falls back to readable English instead of a blank label.

All three locale files are imported statically in `src/i18n/index.tsx`. They end
up inside the precached bundle, which is deliberate: a language switch has to
work in airplane mode. An i18n library that fetches translations over HTTP is
the one thing an offline-first app must not do. The whole translator is about
40 lines; three locale files add roughly 12 KB to the bundle.

## Files

```
apps/web/src/i18n/
├── index.tsx              ← provider, useI18n(), useFormat()
└── locales/
    ├── en.json            ← UI strings only
    ├── hi.json            ← UI strings + engine strings
    └── mr.json
apps/web/src/ui/LanguageSwitch.tsx
packages/engine/src/i18n.ts   ← Translate type, fmt(), English fallback
```

## Using it in a component

```tsx
import { useFormat, useI18n } from '../i18n/index.js';

export function Thing() {
  const { t } = useI18n();
  const f = useFormat();
  return <p>{t('status.pending', { n: 3 })} — {f.money(20159)}</p>;
}
```

`{n}` style placeholders, no plural rules. If you hit a case that genuinely
needs plurals, add two keys (`x.one` / `x.other`) rather than reaching for a
library.

## Adding a language

1. Copy `locales/hi.json` to `locales/pa.json` and translate the values. Leave
   the keys exactly as they are.
2. In `src/i18n/index.tsx`, import it and add it to `LANGS`:
   ```ts
   import pa from './locales/pa.json';
   export const LANGS = { en, hi, mr, pa } as const;
   ```
3. Add the locale tag: `const LOCALE_TAG = { ..., pa: 'pa-IN' };`
4. Set `"lang.name": "ਪੰਜਾਬੀ"` at the top of the file. The switcher reads it.
5. If the script is not Devanagari or Latin, add the font to `index.html` and
   extend the `:lang()` rule in `styles.css`.

That is the whole process. No build step, no extraction tool, no keys to
register anywhere else.

## Things that bit us, so you do not have to

**Numerals.** `Intl` renders Marathi numbers in Devanagari digits (₹२०,१५९)
while Hindi stays Latin, so one screen showed two numeral systems. Every
formatter now pins `-u-nu-latn`. Farmers read Latin digits on every mandi board
and receipt, so this is also the right call for users, not just for consistency.

**Line height.** Devanagari sits taller than Latin at the same font size.
`styles.css` gives `:lang(hi), :lang(mr)` a slightly looser line-height rather
than switching family — Noto Sans covers both scripts at matching weights,
which is why it was chosen.

**Label width.** Marathi and Hindi labels run 20–40% longer than English. The
parameter panel uses `justify-content: space-between` rather than fixed column
widths for exactly this reason. Test at 360px in all three languages before you
call a layout done.

**Crop names.** These live in the locale files, not in `model.json`. The model
file holds numbers and their sources; anything a user reads belongs here.

## Checking your work

```bash
npm test                 # includes a test asserting the engine emits keys, not text
```

Then load the app, switch language, and check three things: the "Why this
result" bullets, the risk driver names, and the freshness badge. If those three
follow the language, everything does — they are the ones that come from the
engine rather than from a JSX label.
